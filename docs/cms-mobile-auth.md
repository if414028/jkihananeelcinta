# Mobile authentication with the CMS

Firebase Authentication still owns email/password, ID tokens, password reset, and logout.
Login and startup call `POST /api/v1/auth/session`. Registration creates a Firebase
account first, then sends the complete registration profile to `POST /api/v1/auth/register`.
The app caches the CMS profile for the existing screens; it does not cache bearer tokens
or passwords and does not reuse the legacy cached profile to authorize access.

The app reads `data.profile.role` from the CMS response. `SuperUser` restores the
existing admin menus and actions, including Green Room. `User`, a missing role,
or an unknown role maps to the local legacy `Jemaat` role without admin menus.
Login and startup save the fresh CMS role before opening the home screen; the
same mapper applies to registration and `/me` recovery responses. Role is never
sent in the registration payload.

## Development server

`CMS_API_BASE_URL` in `app/build.gradle` currently uses
`http://76.13.22.241:8081/api/v1`. Android's network security configuration permits
cleartext for that IP. When the domain and HTTPS are ready, update the build constant
and remove the IP exception from `app/src/main/res/xml/network_security_config.xml`.

## Recovery

- A CMS `401` refreshes the Firebase ID token and retries once. A second `401`
  clears the local profile and signs out of Firebase.
- `403` does not trigger automatic registration. The user is asked to contact the
  church administrator for an unlinked, inactive, or conflicting profile.
- A timeout/network failure, server failure, or registration `409` checks `GET /me`
  to recover a registration that already committed. An unresolved `409` asks for admin help.
- Failed CMS signup leaves the Firebase account intact. The app remembers the UID
  of its unfinished signup locally so the registration form can retry with that
  account, including after reopening the app. Other existing Firebase accounts
  cannot be registered merely because login returned `403`.
- Validation errors display the API's field errors. `429` respects `Retry-After`
  (seconds or HTTP date); absent that header, subsequent attempts use an exponential
  cooldown. Volley never automatically retries a POST.

## Scope of this migration

The active signup form retains every original field, grouped into account, personal
information, profile/education, baptism/church, family, and photo/confirmation. The
original San Francisco font assets remain in use. NIJ is generated by CMS; credentials
and admin roles are excluded from the registration payload.

**CMS API follow-up required:** the deployed API currently ignores legacy profile fields
and does not accept the mobile photo upload. The user will update the CMS API to match
[the complete mobile contract](register-cms-payload.md). Mobile sends JSON without a
photo, or multipart form data with a JPEG `profile_photo` when one is selected. Nothing
is uploaded to Firebase Storage in registration. End-to-end persistence of restored
fields requires the updated CMS validation, storage, and profile response.

Automatic FCM and last-open writes to Realtime Database have been removed from the
authentication/startup path. FCM topic subscriptions and notification delivery remain;
the documented API has no device-token endpoint yet. Other content, pastoral tools,
and profile editing screens still use legacy database integrations and need a separate
migration before Realtime Database can be fully retired.

## Manual checks on an Android device

1. Login with an existing Firebase UID mapped in CMS: name and NIJ should match CMS.
2. Reopen the app: the CMS session must succeed before opening the home screen.
3. Register a new account: verify CMS generated its NIJ and Firebase owns the password.
4. Interrupt the CMS signup connection; retry with the same email. Verify one profile,
   no Firebase account deletion, and recovery through `/me` if the request committed.
5. Test an unmapped/disabled account, validation failure, and rate limit response.
6. Logout: Firebase session and local profile should be cleared.
7. Login with `data.profile.role = SuperUser`: Green Room and existing admin
   actions should appear. Login with `User`: those controls should be hidden.
   Change an admin to `User` in CMS and reopen the app to check the refreshed role.

Automated recovery/mapping tests: `./gradlew :app:testDebugUnitTest`.
